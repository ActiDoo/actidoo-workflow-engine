# Frontend tests

Three kinds, picked by what the test needs to see:

| Kind | Where                                   | Runs in                      | Use for                                                                          |
| ---- | --------------------------------------- | ---------------------------- | -------------------------------------------------------------------------------- |
| Unit | next to the code, `src/**/*.test.ts(x)` | jsdom (project `unit`)       | pure functions and small components (FEEL evaluation, normalisation, formatting) |
| Form | `src/test/workflows/`                   | Chromium (project `browser`) | one form as the user sees it: rjsf, hide-if, validation, submit payload          |
| App  | `src/test/app/`                         | Chromium (project `browser`) | behaviour across pages on a real store, with a fake BFF                          |

```bash
yarn test                        # everything (what CI runs)
yarn vitest --project unit       # jsdom tests, watch mode
yarn vitest --project browser    # Chromium tests, watch mode
```

Conventions for the browser tests:

- Interact and assert through Vitest's browser locators — `page.getByRole/getByText/...`,
  `expect.element(locator)` — plus the project's `getById` (rjsf field ids) and, only for
  controls inside a shadow root without role/label, `getByCss` (`support/locators.ts`).
  They look through shadow DOM (UI5 web components) and retry until the test times out, so
  tests do not poll or query the DOM themselves.
- The HTTP layer is replaced per test file by `support/fakeFetchService.ts`: one `vi.mock`
  line for `FetchService` and a handler registered with `useFakeBackend`.
- Fixtures are BFF responses generated by the backend, see `workflows/README.md`.

Details: `workflows/README.md` (form tests, fixtures) and `app/README.md` (app tests).
